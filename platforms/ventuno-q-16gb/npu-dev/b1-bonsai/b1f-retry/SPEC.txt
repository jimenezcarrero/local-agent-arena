B1f: the htp_main_thread retry patch (#30309) built for ff5a2337, and a 9B parity check on it. PROPOSED for review,
written 2026-10-21 after B1d-9B's PASS (b1d-9b/RESULT.txt), as the first step towards a V0e plan for the 9B: the owner
asked which build V0e should use; the patched one is chosen here, for the reasons below ("So if the patch is clear pick
why do you ask me?"). Nothing runs on the NPU before this spec's review, merge and the owner's approval; the laptop
build is the owner's step (the board has no Hexagon toolchain, D129).

1. Why the patched build for a V0e of the 9B
  The unpatched htp_main_thread (ggml-hexagon/htp/main.c) leaves its loop on any dspqueue_peek error other than
  EWOULDBLOCK/EEXPIRED; that session's queue is then never read again and the process hangs (F1, D127; #30309).
  ff5a2337 does not change that loop (b1-bonsai/README.txt "Known risk"; the patch applies with a 90-line offset only).
  The retry patch logs the error (rate-limited), sleeps 1 ms and retries (upstream/htp-main-thread-retry.patch.txt,
  sha256 4b9838df...). Observed on this board with the campaign's 836d57176 package: 8 single AEE_ENOMORE events in
  90 minutes of six sessions with the patched library, each followed by continued service (D133); later V0e runs on
  two sessions logged 0-3 retry events each. With the unpatched library each such event would, by the F1 mechanism, have
  been a hang (an inference from one observed hang). Counter-evidence, stated: V0e B4 (Ternary-Bonsai-2-4B, one session,
  ff5a2337 unpatched, D179) ran S1 and S2 with 0 faults, and B1's ff5a2337 runs (minutes each) had none. The 9B runs on
  two sessions, the configuration in which the events were logged. The patch's cost is a build and a short check; its
  benefit is that the known failure becomes a logged, counted retry (more than 1 in a row flagged to the owner, D136).
  Correction recorded: in the agent's message of 2026-10-21 B4's unpatched V0e was left out ("the B1 runs on ff5a2337
  were all unpatched with zero errors, but they lasted minutes").

2. Build (laptop, the owner's step): phase-v0/tools/build_htp_retry_x86.sh from the commit that merges this spec, with
  its new HTP_COMMIT/HTP_RELEASE_SHA option (mocked tests test_build_htp_retry.sh 10/10, 4 of them new):
    curl -fsSL https://raw.githubusercontent.com/jimenezcarrero/local-agent-arena/<merge commit>/platforms/ventuno-q-16gb/phase-v0/tools/build_htp_retry_x86.sh -o build_htp_retry_x86.sh
    HTP_COMMIT=ff5a23376725e5a889fa0bfb987b7541dc304da0 \
    HTP_RELEASE_SHA=76603cb189e70e3e0d418c1dcbad0a4fcd706544378df679337f3fe81b80d8df \
      bash build_htp_retry_x86.sh arduino@<board>
  (with docker as the owner's Docker needs, as in D131). The script builds the control (unpatched) and the retry
  library from a fresh clone at ff5a2337 with the B1a package's image (sha256:41b710ee...) and SDK line, checks the
  patch (sha256, 1 file), the patch's string in the retry library only, writes the manifest and copies one tarball to
  ~/v0/ on the board with a sha256 check. HTP_RELEASE_SHA is the ff5a2337 package's libggml-htp-v75.so (its manifest).
  Gate: DONE; the manifest's "control == release bytes: yes" (the toolchain reproduces the measured DSP binary, as for
  836d57176 in D131); if it is "no", the stage stops and the owner decides (the retry library's toolchain equivalence
  would be unproven).
