Developer plan: faster prompt reading for LFM2.5-24B-A2B on the Ventuno Q NPU (resident Q2_K, and Hexagon "op offload")
Revision 3, 2026-10-14. Revision 1 (c4be600) and revision 2 (077e32b) were reviewed by Codex the same day; this revision
answers the review of 077e32b (four inline findings and five requests) and Codex's placement correction (section 12).
Revision 2's answers to the first review are in section 10, my own additions in section 11. Owner: "let's PR a
complete developer plan that codex can review for the NPU improvements" and "Review PR57, think in how to improve the
plan and if there is something still missing" (2026-10-14).
This is development work, separate from the V0 campaign: nothing here changes the campaign's measured package,
configuration, tools, monitor files or evidence, and no result here is campaign evidence or qualification. Nothing runs
on the NPU until the owner approves this plan after review, and again before each NPU stage (section 7).

0. Summary
  LFM2.5-24B-A2B (lfm2moe; 23.97B parameters, of which 22.95B are the 64 experts of 38 MoE layers; 2.45B active per
  token, top-4) runs on this board on the CPU only. Exploratory CPU figures (IQ3_XXS file, exploratory-lfm25-cpu/, not
  a matched control): llama-bench pp512 15.81 / tg128 9.13 tok/s at depth 0 and 13.31 / 5.90 at depth 8192; server
  prompt reading 15.6 tok/s. A 32K-token fresh context takes over 30 minutes to read.
  Two tracks, in this order:
    Track R (no backend code): since upstream #30035 (2026-10-12, after the campaign's release 836d57176), the NPU keeps
      Q2_K weights at their file size (2.625 bits per weight) instead of 4.0. A Q2_K LFM2.5 would need about 8 GB of
      NPU-mapped memory, which may fit fully on the NPU across three sessions. If it fits and its quality is acceptable,
      prompt reading moves to the NPU's matrix unit with no new code.
    Track O (new code): "op offload". Keep the weights in CPU memory and, for large-batch matrix operations only, copy
      them to the NPU, compute there, and discard the copy. llama.cpp does this for CUDA, Vulkan, Metal, SYCL and CANN;
      the Hexagon backend leaves the hook empty. This serves files that do not fit on the NPU (3-bit and larger), and
      is the general mechanism worth contributing upstream.
  Both tracks start with offline stages; the first NPU time is a small, approved probe.

1. Facts (llama.cpp 836d57176 = the campaign's release, ~/v0/llama.cpp; "master" = ggml-org master af0579c78,
   2026-10-14; line numbers are 836d57176's unless marked master)
  F1 The hook is empty: ggml-hexagon.cpp:8311 "/* .offload_op = */ NULL, // ggml_backend_hexagon_device_offload_op,",
     since the backend's first commit (63d2fc46e, #16547); still NULL on master (:9612). No upstream issue or PR found
     (GitHub search of ggml-org/llama.cpp, 2026-10-14: "hexagon offload", "hexagon moe", "hexagon op offload").
  F2 Scheduler (ggml-backend.cpp): an op whose weight (buffer usage WEIGHTS) is in a host buffer of the lowest-priority
     backend is assigned to a higher-priority backend b if supports_op and offload_op are both true (:1105-1116). A
     weight on an incompatible backend starts a new split, so that the memory of previously offloaded weights can be
     reused (:1474-1484). Each copy is made with ggml_dup_tensor_layout and named "<backend>#<src>#<c>"; it is marked
     INPUT/OUTPUT only when n_copies > 1 (:1515-1528). At compute, a whole weight goes through
     ggml_backend_tensor_copy; for MUL_MAT_ID it copies only the runs of used experts with
     ggml_backend_tensor_set_async at raw byte offsets (expert_offset = id * nb[2]) plus up to 512 bytes of padding into
     the next expert (:1845-1934). Hexagon's set_tensor_async is the synchronous set_tensor (:7823-7828).
     CUDA's hook: get_op_batch_size(op) >= GGML_OP_OFFLOAD_MIN_BATCH (default 32; batch = ne[1] for MUL_MAT, ne[2] for
     MUL_MAT_ID; ggml-cuda.cu:5734-5752). --no-op-offload disables offload globally.
  F3 NPU weight types (ggml-hexagon.cpp:6184-6300): MUL_MAT and MUL_MAT_ID for Q4_0, Q4_1, Q8_0, IQ4_NL, MXFP4, Q4_K,
     Q5_K, Q6_K, Q3_K, Q2_K (and F16/F32 for MUL_MAT); not IQ2/IQ3 types or IQ4_XS. All repack types are HMX-eligible
     above HTP_MM_HMX_MIN_NROWS rows (:297, :5097-5140). SSM_CONV is supported.
  F4 Tiled layout ("repack"). The NPU computes on weights in its own tiled layout. get_alloc_size returns the tiled size
     for every Hexagon buffer (:2769), but set_tensor repacks only tensors flagged GGML_HEXAGON_TENSOR_REPACK: weights
     in WEIGHTS buffers, or tensors that supports_op put in sess->needs_repack, which happens only when the weight has no
     buffer yet (:2408-2440, :797-815, :6222-6224). Partial writes go to a shadow buffer and are repacked when
     shadow_size >= ggml_nbytes (:2427-2440). A scheduler copy in a COMPUTE buffer is therefore memcpy'd raw today.
     Tiled sizes per 32x32 tile (htp/matmul-ops.h): 836d57176: Q3_K 512 B and Q2_K 512 B (4.0 bpw each);
     master: Q3_K 512 B (4.0 bpw), Q2_K 336 B = file size, ggml_row_size (2.625 bpw; #30035, master :328-342).
  F5 One NPU session addresses about 3.2 GB (HTP_OP_MAX_VMEM_DEFAULT 3,355,443,200, htp-ops.h:134). Several sessions
     on one NPU split layers between them (GGML_HEXAGON_DEVICES=N, docs/backend/snapdragon/README.md).
  F6 Sizes for LFM2.5-24B (header of the Hub files, 2026-10-14). Expert tensors: 3 per MoE layer, 2048 x 1536 x 64 =
     201M parameters each (Q3_K tiled: ~101 MB; Q2_K on master: ~66 MB). All experts: Q3_K tiled ~11.5 GB (does not fit
     on the NPU); Q2_K on master ~7.5 GB, plus ~0.6 GB of other weights. The published 2/3-bit files store experts in
     IQ types (unsloth UD-Q3_K_XL: IQ3_XXS/IQ4_XS; UD-Q2_K_XL: IQ2_XS/IQ3_XXS; AtomicChat AD-IQ3_XXS/IQ3_M); Liquid's repo
     has Q4_K_M 14.5 GB, QAD-Q4_0 13.6 GB and larger. A file with NPU-type experts must be made with llama-quantize.
  F7 Memory: 16 GB board, MemTotal ~14 GiB, ~13 GB available idle. CPU and NPU share DRAM.
  F8 CPU (sysfs cpuinfo_max_freq and /proc/cpuinfo on the board, 2026-10-14): cpu0-1 Cortex-A78C up to 2.112 GHz
     (cpufreq policy0), cpu2-3 Cortex-A78C up to 2.3616 GHz (policy2), cpu4-7 Cortex-A55 up to 1.9584 GHz (policy4); the
     four A78C cores do not share one maximum. asimddp, no i8mm, no SVE. Every run records the governor and the
     per-policy frequencies before and after. llama.cpp's CPU repack buffer (CPU_REPACK;
     ggml-cpu/repack.cpp:4974-5072: Q4_0, Q4_K, Q2_K, Q5_K, Q6_K, IQ4_NL, Q8_0 by CPU feature) has no is_host
     (:5248), so the scheduler does not offload from it (F2).
  F9 Campaign observation, corrected (campaign D170, Codex review of the campaign's 3b9b5c8): NeoHorse's logits depart
     from the CPU at full offload with multi-token ubatches (KLD 0.817) and are near the CPU with -ngl 32 (0.0024) or
     -ngl 16 (0.00028). On the pinned loader -ngl 32 puts block 0 on the CPU and blocks 1-31 AND the output layer on the
     NPU (i_gpu_start = n_layer_all + 1 - ngl; tied token_embd duplicated as the OUTPUT tensor), so the output layer
     was on the NPU in every arm; the earlier "output layer" localization is withdrawn, no mechanism is localized, and
     this plan assumes none. A32 is a measured mixed placement (block 0 on the CPU), not a known-good calibration
     reference and not an output-on-CPU configuration.
  F10 Master's copy boundary (af0579c78, 2026-10-14T06:23:44Z). ggml-backend.h:320-327: ggml_backend_sched_copy_callback
     (backend, src, dst, graph, user_data), called only for input weights in host buffers, after all non-weight inputs
     of the split are copied; returning false makes the scheduler copy the whole weight. ggml-backend.cpp:1886-1896
     copies non-weight inputs first, then host weights; :1847-1849 calls the callback; on false, :1854 tries
     cpy_tensor_async and falls back to ggml_backend_tensor_copy. llama-context.cpp:711 installs sched_copy_experts;
     :2762-2843: if the split's first node is MUL_MAT_ID on dst, it reads the ids with ggml_backend_tensor_get_async +
     synchronize (:2791), builds the used-expert set once per ids tensor (reset per graph compute, :2750), and writes

  F11 Master's MoE cache (llama-moe-cache.cpp, --moe-cache-mib, default 0 = off): per-layer expert banks in a device
     buffer, sized from the raw expert stride (GGML_PAD(nb[2] * (n_slots + 1)), :275), filled with set_tensor_async at

2. Goals and gates (all measured; none assumed from estimates)
  G1 Backend parity (numerics of the NPU path, not model quality): teacher-forced per-position comparison of the NPU
     arm against the matched same-file CPU arm, identical token ids and positions (T3a), within the fixed thresholds of
     section 5; all outputs finite.
  G2 Faster: fresh prompt reading >= 2x the best matched CPU arm on the same file, at depth 0 and 8192 (end-to-end
     llama-bench pp512 and server time to first token on a fresh prefix; reported separately).
  G3 Writing not slower: tg128 >= 95 % of the better matched CPU arm (faster passes).
  G4 Agent screening on fresh prefixes (T5), with the numeric rule of section 5; a screening result, not a reliability
     claim.
  G5 Safe: no DSP fault, hang, kernel error or memory floor breach in any accepted run (section 7).
  G6 Off by default (Track O): with the opt-in unset or 0, the graph's backend assignment and the outputs are identical
     to the unpatched build at the same commit.
  G7 Model quality of a candidate file (M2, M3), screened on the x86 host before any NPU stage that uses it (T7): the
     quantized file on the CPU against REF (Q8_0), plus the agent-task rule. A separate gate from G1: a file can match
     its own CPU run perfectly and still be poor, and CPU repeatability says nothing about quantization loss.
  Feasibility rule (Track O): the early decision uses a measured range, not a point estimate (section 4, A2). Track O
  stops before NPU time only if the optimistic bound of that range is below 2x; if the range straddles 2x, an
  owner-approved small probe (stage C1) resolves it. Track R stops if the file does not fit (R1) or fails G7 (T7, before
  R2), or G1 fails on the NPU (R3).

4. Track O design and offline stages
  D1 Hook ggml_backend_hexagon_device_offload_op(dev, op) returns true only if all hold:
       - GGML_HEXAGON_OP_OFFLOAD=1 (unset or 0 = off; G6);
       - op is MUL_MAT (prototype phase O1) or MUL_MAT_ID (phase O2, after D3 passes its tests);
       - src0 is a repack type and is not on the deny list: the output projection (output.weight, or token_embd.weight
         in its OUTPUT role for tied models, F12). Reason: cost (a 128000-row weight copied per ubatch for a matmul
         whose server batch is usually 1 output row) and the unresolved full-offload divergence (F9), not a localized
         fault; offloading it is a separately declared experiment. Matched by weight identity and op role, verified per
         run (K7);
       - batch >= GGML_OP_OFFLOAD_MIN_BATCH (default 32), defined as in CUDA (F2);
       - the tiled copy fits the session's remaining VA and the declared staging budget (D4); otherwise false.
       Preferred route (A1 decides, F10): the explicit copy boundary of master's scheduler copy callback, not D2's
       address-range inference. The callback is installed by llama_context (sched_copy_experts); a Hexagon-aware path
       composes with it (the MoE cache first, then the expert runs, then the full-copy fallback when it returns false),
       never replaces it silently. The backend learns the epoch and the routed set either from a small backend
       function the composed callback calls (looked up through the registry's proc-address table) or by reading the
       ids itself (D3). D2's address-range lookup remains the fallback if A1 finds a copy path the callback does not
       cover.
  D2 Copy identity, copy epochs and repack (answers Codex Q1, finding 2 of the first review, and the copy-epoch finding
     of the second). No name or INPUT-flag inference.
       - When offload_op accepts an op, the session records an offload source entry: source weight pointer, its data
         range [data, data + nbytes), type, shape and nb, and a role (dense or expert tensor).
       - Copy epoch: one epoch per (destination, copy of one split input). It opens at the first weight write into the
         destination after the epoch was closed (or at the composed callback's begin call, F10), and every range write
         of that copy joins it; it closes at dispatch. A new epoch opens on the next copy into the destination, and
         all coverage is dropped when the destination's buffer is reassigned or the graph is reallocated.
       - Per-write versions are separate from the epoch: each write gets a version number for tracing, but validity is
         decided per epoch from its accumulated coverage (dense: byte ranges; expert tensors: per-expert bits, D3).
       - Hexagon set_tensor on a non-WEIGHTS buffer looks up the source range that contains [data, data + size). On a
         match with the destination's type and shape, the write is a weight copy: it is repacked at the translated
         tiled offset and its range added to the epoch's coverage. A write that does not match (a partial or unknown
         write) removes every intersected range, or every intersected expert, from the coverage.
       - At dispatch, a MUL_MAT whose src0 is a repack type in a non-WEIGHTS buffer needs full coverage in the current
         epoch; a MUL_MAT_ID needs every routed expert covered (D3). Otherwise the backend aborts the graph with an
         error (fail closed) and never computes on raw or stale data.
       - The table is cleared when the session's graph is rebuilt; entries do not outlive the source buffer.
       Repack-at-use is kept only as a fallback design if neither the callback boundary nor the source-range lookup is
       reliable in A1; it would carry the same epoch rule and an accounted scratch buffer.
  D3 MUL_MAT_ID range writes (finding 1). The scheduler writes runs of used experts at raw offsets with up to 512 bytes
     of padding into the next expert (F2). Phase O2 handles this explicitly:
       - expert index from the raw offset (offset / nb[2]); each fully covered expert is repacked into its tiled slice
         at id * tiled_expert_size; bytes of padding that spill into a following expert are ignored for that expert;
       - per expert, a covered bit in the current epoch (D2). The dispatch check requires the bit for every expert id
         the op actually routes to, read from the routing ids of this dispatch. Sources, in A1's order of preference:
         the used set that the composed copy callback already computed from the ids (F10), handed to the backend with
         the epoch; or the backend reads the ids tensor itself before dispatch (Hexagon buffers are not host buffers,
         so this is a get_tensor with a synchronize; T4 measures its cost); or a verified whole-tensor copy (the
         callback returns false, D2's dense rule). If none of these is available, MUL_MAT_ID is not offloaded. There
         is no weaker "every written expert" check: it cannot show that every routed expert was written;
       - Q3_K/Q2_K repack helpers that assume offset 0 and whole tensors (they clear a whole slice) are wrapped per
         expert slice; no concurrent calls into the same slice.
     Until O2's tests pass, MUL_MAT_ID is not offloaded (phase O1 is dense MUL_MAT only).
  D4 Memory accounting. Count, per split and at peak: tiled destination copies, shadow/staging buffers, compute
     buffers, KV and recurrent state, and every buffer mapped in each session. Start with n_copies = 1 (no pipeline
     parallelism), then test n_copies > 1 explicitly. Bound: the peak must fit one session's VA (F5) and the run's
     memory floor (section 7); the hook refuses offload that would exceed the declared budget.
  D5 Repack speed. Measured first (A2). If parallelised, partition by disjoint tiles/expert slices, clearing Q3_K/Q2_K
     destinations once per slice.
  D6 Placement for runs: weights on the CPU (-ngl 0, or -ngl all with --override-tensor keeping matrix weights on the
     CPU and the rest resident), --no-repack (F8), the output projection not offloaded (D1). Exact lines frozen per K5;
     the resulting placement verified per run (K7).
  D7 Options after O1/O2 work (each a separate, budgeted experiment):
       - a bounded resident cache of small or hot weights, sized from measured reuse;
       - CPU repack kept for tensors that are never offloaded, if --no-repack measurably hurts decode;
       - an allowlist of dense ops on the original IQ3_XXS file (experts stay on the CPU), a same-file experiment that
         needs no new quantization; its gain is unknown and probably small (experts are ~96% of the weights).
  Offline stages (no NPU; the board idle and no campaign session, or the x86 host where stated):
    A1 Trace and record (file:line, at the pinned master commit, which is the commit of K1 and F10): how split inputs are
       created, allocated and reused (ggml-alloc), which copy paths reach the Hexagon buffer (the copy callback and its
       full-copy fallback, ggml_backend_tensor_copy -> set_tensor, set_tensor_async, cpy_tensor_async, set_tensor_2d),
       the MUL_MAT_ID path through sched_copy_experts, the MoE cache path (F11), and how the scheduler starts new splits
       for offloaded weights. Decide: the epoch boundary (callback or address range), the routed-set source (D3), and
       how a Hexagon-aware callback composes with llama_context's. Settle D4's peak with references.
    A1b MoE cache audit (offline): bank sizing and views (raw nb[2] stride) against Hexagon's get_alloc_size and tiled
       expert slices; whether its copy_async views and slot maps can be made layout-aware. --moe-cache-mib stays 0 in
       every baseline and test arm until this audit and a separately declared test say otherwise.
    A2 Repack and copy cost on the target ARM cores (the board, idle): a harness built from the pinned source's repack
       functions, on real M2/M3 tensor data (read from the GGUF on the x86 host, a few tensors copied to the board, or a
       synthetic tensor with the same type and shape), measuring: source-read bandwidth (cold mmap and warm page cache),
       tiled-write bandwidth, repack GB/s per type on 1 and 4 A78C threads. Produce optimistic and pessimistic bounds for
       pp512 at depth 0 and 8192, including residual CPU ops (measured from CPU-B with GGML_SCHED/perf timings), the
       NPU compute range (from NeoHorse's HMX throughput as the optimistic end; from a pessimistic per-expert row padding
       factor of 32/active rows), synchronization and page faults. Apply the feasibility rule (section 2).
    A3 Code D1-D3 on a branch of a fork at the pinned commit, host side only, with host timers and byte counters
       (bytes read, bytes written tiled, repack time, copy time, sync time) printed per graph at a verbose level.
    A4 Offline tests without the NPU (x86 host or board, CPU only, using the backend's host-side code with a mocked
       session where possible), run before any device probe: the D2 lookup and epoch rules (matching copy,
       non-matching quantized input such as a Q8_0 KV view, rewritten input, address reuse across graphs, buffer
       reassignment); copy-epoch and coverage cases: a two-range copy (experts {0,1} then {8,9}) in one epoch passes;
       a routed expert omitted from the written ranges fails; data left from the previous epoch fails; a partial or
       unknown write over a covered expert fails; padding that spills into the next expert does not cover it; the D3
       expert translation (sparse, nonconsecutive and changing ids, repeated graphs); the composed callback (MoE cache
       off, expert runs, full-copy fallback when it returns false); threshold boundaries (batch 1, 31, 32, 33); the
       opt-in states (unset, 0, 1, with and without --no-op-offload); and, on the host CPU with the unpatched package,
       that a slot erase (server /slots/0?action=erase, master server-context.cpp:5323) followed by the same request
       gives cache_n = 0 on a hybrid recurrent model (T5's fresh arm depends on it).

5. Tests on the NPU (each listed with the stage that runs it, section 6)
  T1 Off by default (G6): patched package with the opt-in unset/0 vs the unpatched package: identical scheduler
     assignment (debug output compared) and identical greedy outputs on the frozen prompts.
  T2 Kernel and copy parity: test-backend-ops -b HTP0 for MUL_MAT and MUL_MAT_ID per repack type at batches 1, 31, 32,
     33, 128, 512, plus a new mode or small harness whose weight reaches the NPU through the offload copy (whole tensor
     for MUL_MAT; sparse, nonconsecutive, changing expert ids and repeated execution for MUL_MAT_ID).
  T3a Backend parity (G1): on the frozen text (K5), several sequences and positions, ubatch 512 and 2048, identical
     token ids and positions in both arms: per-position KL divergence, top-1 agreement and the rank of the CPU's top
     token, NPU arm against the matched same-file CPU arm. Thresholds fixed now, in the manifest before any NPU result,
     never enlarged afterwards: mean KLD <= 0.01, 99th-percentile KLD <= 0.10, top-1 agreement >= 97 %, every value
     finite. Basis: the campaign's NPU path with block 0 on the CPU measured 0.0024 / 97.9 % on NeoHorse, and the
     full-offload divergence was 0.817 / 66.0 % (F9); the thresholds allow about 4x the former and reject the latter.
     CPU-A vs CPU-B and a CPU repeat are reported as the noise floor; they do not set the threshold. Perplexity is
     secondary.
  T7 Model quality (G7), on the x86 host, before the file's first NPU stage: the candidate on the CPU against REF (Q8_0)
     with the same token ids, positions and reference settings (pinned in K5): mean KLD, top-1 agreement, rank of REF's
     top token; and T5's fresh-prefix screening on the host CPU for the candidate and for REF. Pass: top-1 agreement vs
     REF >= 90 %, and T5's rule (below) for the candidate with REF's count as the comparison. Fixed now, not adjusted
     after results.
  T4 Speed: llama-bench pp512, pp2048, tg128 at depth 0 and 8192, ubatch 512/1024/2048, 3 repetitions, per arm (K4);
     host counters (A3) and DSP op timing (GGML_HEXAGON_PROFILE=1) for one run per arm; major page faults and disk reads
     during the run. Reported separately: fresh time to first token (server, fresh prefix, 2K/8K/16K tokens), cached
     tool-turn latency, and decode speed.
  T5 Agent screening (G4), per arm on the same file. Fresh arm: a server with -np 1 and --cache-ram 0, and the slot
     erased (POST /slots/0?action=erase, slots endpoint enabled) before each trial; a trial counts only with
     cache_n = 0 and prompt_n equal to the whole prompt, and for NPU-O only if its host counters (A3) show positive
     offloaded bytes and offloaded ops in every evaluated ubatch whose batch is at or above the declared threshold, with
     at least one such ubatch (a final remainder ubatch below it is not offloaded; n_ubatch and the ubatch sizes are
     recorded). The erase on a hybrid recurrent model is checked on the host CPU first (A4). Warm arm: the same
     requests served from a warm cache, labelled as such (TTFT warm), never pooled with the fresh arm.
     20 fresh and 20 warm trials over the frozen requests; each request has an expected tool behaviour in the K5 table
     (tool name, required argument keys, values that must match). A trial passes if the first reply is that call,
     its arguments parse as JSON, match the schema and the expected values, and it has an id. Rule, per arm and kind:
     passes >= 17/20 and >= (the better matched CPU arm's passes - 2). Plus one streaming pi smoke per arm with a tool
     result and a tool error (recovery observed; 7/7 checks). A screening result only.
  T6 Robustness: 10 consecutive fresh 8K-token prompts, then 10 more after 5 minutes idle, server mode.

7. Safety, enforcement and separation (finding 7)
  - Exclusivity: immediately before every NPU run, the wrapper checks that no campaign driver, admission, session or
    llama process is running (the campaign's launch-check patterns) and refuses otherwise.
  - Wrapper npu_dev_run.sh (new, under npu-dev/tools/, tested offline before C1/R2) runs every executable of every
    stage (llama-server, llama-bench, llama-perplexity, test-backend-ops, harnesses):
      * per-run timeout (declared per command);
      * live memory floor: samples MemAvailable every second and sends SIGTERM, then SIGKILL, below 1.5 GB;
      * stall: a process with a thread in fastrpc_wait_for_completion and < 0.5 core-s per 10 s for 120 s is killed (the
        campaign watchdog's rule, applied to any binary);
      * before and after: DSP journal read and kernel log audit, both fail-closed (a failed read is a STOP); any fault
        line, "dspqueue" error or hang ends the stage;
      * evidence only under ~/bench-runs/npu-dev/<stage>/<run>/ (commands, env, package and model hashes, stdout,
        stderr, timings, memory samples, verdict).
  - The campaign's npu_stall_watchdog.sh keeps running (it watches llama-server/llama-bench by name and writes to the
    campaign's npu-stalls/status paths). It is not modified. Any watchdog line written during a development window is
    attributed in the development record (time window, pid, stage) and noted for the campaign record.
  - Allocation guard: the hook (D1/D4) and the wrapper's preflight refuse a configuration whose declared peak mapped
    and staging memory cannot fit; nothing is allocated or dispatched past that point.
  - On a DSP fault, hang or kernel error: stop the stage, do not repeat the configuration, record it, tell the owner.
    The root helper /usr/local/sbin/v0-cdsp-restart is not used (authorization expired 2026-10-09); recovery is the
    owner's decision (e.g. reboot).
  - Identity records before and after each development window: the campaign package's file hashes, the patched DSP
    library and .farf identity, the measurement checkout, the dpkg baseline; after the window, the campaign's launch
    checks run before any campaign session.
  - No vendor files, sudoers, system packages or root.

11. Added from my re-review of revision 1
  - Track R. Revision 1 assumed Q2_K costs 4.0 bits per weight on the NPU (true at 836d57176). On master it costs the
    file's 2.625 (#30035), which makes full NPU placement of a Q2_K LFM2.5 plausible (~8 GB over three sessions) with
    no backend code. It is the cheapest test and goes first.
  - Code base: the plan pinned 836d57176; development moves to a pinned master commit (K1) because the backend changed
    substantially since the release and upstream work must be on master.
  - Sizes corrected from the header: one expert tensor is ~101 MB at Q3_K tiled (revision 1 said 0.25-0.3 GB).
  - Reference quality: revision 1 compared only against the CPU on the same quantized file; a Q2_K or Q3_K_S file can be
    consistent with the CPU and still poor. T3 adds Q8_0 reference logits made on the x86 host.
  - Page cache: with resident NPU buffers, the memory-mapped CPU weights may no longer stay cached; T4 records major page
    faults and disk reads, and A2 measures cold and warm reads.
  - Placement: offload runs keep non-matrix work (attention, short convolution, norms) resident on the NPU where
    supported (D6), rather than leaving it on the CPU with -ngl 0.
