VENTUNO Q benchmark foundation — investigation dated 2026-10-03

PR reviewed: https://github.com/jimenezcarrero/local-agent-arena/pull/38 at `5bf7ef7e97904f845af8cbe8978c866ec6904e49`.

The runbook is a useful starting point, but I recommend fixing route eligibility and documenting the additional qualification below before freezing the campaign. The most promising additional experiment is distributing a larger model across virtual Hexagon sessions. The fastest practical configuration remains unmeasured: this investigation read documentation, source and local benchmark scripts; it did not execute on a VENTUNO Q.

Arduino identifies the board as QCS8275, with eight CPU cores, Adreno graphics and an NPU advertised at up to 40 dense TOPS. It also supports headless access and NVMe expansion. Those TOPS describe an accelerator compute capability, not a language-model token rate. For this campaign, investigate model placement, memory traffic, context, client behavior and sustained clocks together. The MCU is for real-time control and is not an additional LLM compute engine. [Arduino hardware documentation](https://docs.arduino.cc/hardware/ventuno-q/)

Qualcomm's IQ8 brief distinguishes CPU clusters and lists platform memory capabilities. Verify the board's actual SKU, core topology, operating clocks and memory configuration before choosing affinity. Platform maxima are not evidence of this board's achieved RAM bandwidth. [Qualcomm IQ8 product brief](https://docs.qualcomm.com/doc/87-83839-1/87-83839-1_REV_A_Qualcomm_IQ8_Series_Product_Brief________.pdf)

Arduino's instructions identify HTP v75 and publish small-model results around 25 tokens/s on the NPU, versus approximately 7–14 tokens/s on the alternative paths. Its GenieX tutorial was verified with v0.4.0 on Ubuntu 24.04. Treat these as setup references with their original model, prompt and software, not predictions for Ornith-9B at 65K/131K. A substantially faster current build can be valid if placement and methodology explain the difference. [Arduino llama.cpp tutorial source](https://github.com/arduino/docs-content/blob/e54e0f07c8e7cdd130da35f24b78d8be7fbdb99c/content/hardware/ventuno/boards/ventuno-q/tutorials/ai-workflows/llama-cpp/llama-cpp.md), [Arduino GenieX tutorial source](https://github.com/arduino/docs-content/blob/e54e0f07c8e7cdd130da35f24b78d8be7fbdb99c/content/hardware/ventuno/boards/ventuno-q/tutorials/ai-workflows/geniex/geniex.md)

The upstream Hexagon documentation explains a roughly 3.5 GB virtual mapping window per session. Larger models can run through dynamic weight mapping. It also documents layer distribution across multiple virtual sessions on one physical NPU, keeping weights mapped within each session's window. This does not create extra physical compute capacity. It supplies a plausible way to reduce mapping overhead for a 9B Q4_0 model; the actual improvement and memory fit must be measured on v75. [Pinned upstream Hexagon documentation](https://github.com/ggml-org/llama.cpp/blob/836d57176dc699a726c55418e4f96b8ca628e1bf/docs/backend/snapdragon/README.md)

GenieX documents `hybrid` as per-tensor HTP/CPU scheduling, whereas `npu` explicitly selects HTP. Partial `-ngl` offload is a separate experiment that divides layers. These options should be named separately in results rather than grouped into one CPU+NPU result. [GenieX placement documentation](https://github.com/qualcomm/GenieX/blob/a5c8e7fb4a364ddcccefbf187afd1bac52d88de5/docs/en/get-started/platforms.mdx)

The current latest release is GenieX v0.8.0, published October 2, 2026, with source commit `a5c8e7f`. This is not the tutorial's older runtime. Capture the installed CLI version, underlying llama.cpp/QAIRT versions and binary hashes; tag names alone do not describe every dependency. [v0.8.0 release](https://github.com/qualcomm/GenieX/releases/tag/v0.8.0)

Its internal `notes/run.md` describes older fixed pinning and automatic Q8_0 cache behavior. At the inspected v0.8.0 source, `build_context_params` resolves configured thread counts, chooses platform/device batch and flash-attention defaults, and does not contain that described Q8_0 assignment. Linux NPU threadpool parameters are unpinned. Both hybrid and explicit HTP classify as NPU for this configuration code. Use actual startup logs and the pinned implementation; do not copy a six-thread mask from another Snapdragon machine. [Current configuration source](https://github.com/qualcomm/GenieX/blob/a5c8e7fb4a364ddcccefbf187afd1bac52d88de5/sdk/plugins/llama_cpp/src/params.cpp), [Internal notes for comparison](https://github.com/qualcomm/GenieX/blob/a5c8e7fb4a364ddcccefbf187afd1bac52d88de5/notes/run.md)

For GPU testing, upstream documents recent-driver A6xx IoT support, broader quantization coverage than the older Arduino recipe, Adreno kernels and a compiled-kernel cache. Flash attention is not always faster in this backend. Keep Q4_0 as the controlled cross-route file initially, then examine supported alternatives independently. Vulkan stays exploratory rather than a prerequisite for the campaign. [Upstream OpenCL documentation](https://github.com/ggml-org/llama.cpp/blob/836d57176dc699a726c55418e4f96b8ca628e1bf/docs/backend/OPENCL.md)

The CPU baseline should be competitive. KleidiAI supplies compatible Arm kernels selected at runtime; enabling it does not prove a particular kernel was dispatched. BLAS can improve prompt processing at larger batch sizes but is not documented as accelerating token generation. Compare a sensible Arm CPU build and thread settings before concluding that acceleration wins. [llama.cpp build documentation](https://github.com/ggml-org/llama.cpp/blob/836d57176dc699a726c55418e4f96b8ca628e1bf/docs/build.md)

Do not run every combination of every tuning parameter. Use the 1.5B file to confirm setup, the ~4B file to establish a viable fallback, and the 9B file to answer the primary campaign question. Shortlist the leading qualifying configurations before expensive context and sustained tests. If the mapping-window experiment fails on the shipped v75 driver, preserve the exact error and carry on with the other candidates.

The PR's selection rule currently ranks tool-safe routes by prefill before applying both speed gates. Consider A = 200 prompt tokens/s and 3 generation tokens/s; B = 150 and 6. It selects A and rejects 9B even though B satisfies 145 and 4.4. I reproduced that decision with a small synthetic example. Filter by correctness, memory fit and BOTH speed thresholds first, then apply the ranking within eligible routes. Repeat selection independently for the smaller model if 9B has no eligible route. Choose routes per actual model/quantization/context cell where the later rows require it.

The following qualification should be specified before V1:

1. Repeat V0 speed measurements at least three times per final candidate, with documented warmup, identical sampling/output budgets and interleaved route order. Record median and spread. Freeze the input corpus and its hash; `speed_probe.py` builds prompts from repository Markdown and deliberately varies the prefix, so a moving checkout can change the workload. Record actual prompt counts and reject truncation.
2. Keep fresh-prefix latency and realistic multi-turn reuse separate. The probe's `prefill_tps` is prompt count divided by time to first streamed token; it includes request/template/queue work and is not solely backend prompt evaluation. Preserve server timings alongside it. A second test should reuse a transcript, append tool output, and test compaction/replay while reporting observed cached token counts when available.
3. Add streaming tool-call validation through the same client/provider path that pi uses. Both current `probe_toolcalls.py` gates parse a complete non-streaming JSON response. Validate assembled argument deltas, IDs, names, finish reasons, nested arguments, validation-error correction and multiple calls where the pinned client/model support them. A tiny real-pi smoke session should read a scratch file, make an edit, run a command and recover from a deliberate tool error. Document runtime/template/model classification when a gate fails.
4. Qualify each intended window before allocating arena repeats. A 40,960-token server tested only through ~32K prompts does not prove 65,536 or 131,072 operation. At each target window, test near-limit input plus a reserved reply, tool continuation and compaction. Verify model metadata, runtime acceptance, effective context and pi's advertised window agree. Mark unsupported windows explicitly rather than silently shortening them.
5. Hold finalist processes alive for at least the longest intended uninterrupted session; use a 90-minute initial acceptance interval if it covers the planned workload. Sample temperatures, exposed clocks, memory availability, swap, memory pressure and kernel failures throughout. Compare early/late throughput and record process age and restarts. Start/end thermal snapshots alone can miss throttling or delayed cache growth.

The synthetic route example and script reading above are static verification, not board benchmarks.

Tune only the short list. On CPU, first compare 2/4/6/8 threads and decode versus batch thread counts; map the real big/little core IDs before trying affinity. On accelerated paths, use a small batch/ubatch sweep such as 128/512/1024 where accepted. Change one setting at a time, collect errors, and stop exploring values that cannot fit. Preserve both a documented default run and the tuned configuration so the campaign distinguishes a software-stack result from a controlled placement comparison.

GenieX exposes HTP power modes including `burst` and `sustained_high_performance`. Compare sustained behavior after a clean reload between modes; short bursts do not settle the long-session winner. Keep the supply, cooling, room conditions and background services fixed. Actual wall energy needs an external meter if the board exposes no calibrated counter. [GenieX CLI reference](https://github.com/qualcomm/GenieX/blob/a5c8e7fb4a364ddcccefbf187afd1bac52d88de5/docs/en/run/cli/reference.mdx)

Budget model buffers, active KV/recurrent state, compute buffers, retained prompt caches, the OS, pi and DSP allocations together. Process RSS is useful but is not a complete accelerator memory accounting method. Use system availability, swap and driver allocation logs without double-counting shared pages. Reserve a stated headroom floor before looking at arena scores.

For native llama-server runs, a bounded cache sweep of 0/512/2048 MiB is a reasonable experiment proposal, not a selected optimum. The documented default 8192 MiB is a limit rather than an immediately reserved allocation, and 0 disables the retained RAM cache. Slot count and effective per-slot context must also be captured. Keep the parity lane's exact Jetson cache setting and report fit/failure honestly; publish tuned cache results separately. [Pinned llama-server reference](https://github.com/ggml-org/llama.cpp/blob/836d57176dc699a726c55418e4f96b8ca628e1bf/tools/server/README.md)

Keep exact IQ3_M parity and native Q4_0 results separate. Unsupported accelerator quantization is a compatibility result; converting it to Q4_0 does not preserve parity. Likewise, higher-bit files, alternate sampling profiles, MTP/speculative decoding and architecture changes need independent qualification and labels. Extra memory may improve context or quality without improving tokens/s. Judge the final configuration primarily by successful arena tasks, elapsed time and uninterrupted completion, with throughput explaining the behavior.

QAIRT compiled bundles can be an optional throughput/efficiency exploration after the GGUF agent lane works. Its fixed deployment context and quantization make it a separate lane. Issue #1454 remains open as of this investigation and reports dropped tools in a specific QAIRT VLM path; it does not prove that every current model/runtime combination fails. Require the same actual tool gates before admitting any QAIRT configuration to pi arenas. [Tool-call issue](https://github.com/qualcomm/GenieX/issues/1454)

Recommended handoff: update only the Ventuno runbook in PR #38 with the eligibility fix, virtual-session candidate and qualification requirements. Put streaming probe support and any GenieX launch/health/restart/context adapter in a separate shared-suite PR, as the repository requires. After review, inventory the real board, run V0, publish the entire matrix and failure classifications, and freeze the chosen configurations before V1. Keep the 32K crusher's existing pi behavior and the new holdout/stall audits intact for parity.

The 145/4.4 gates can remain preregistered campaign admission thresholds, but the inference that halving speed doubles arena time is only a heuristic. Prefix reuse, tools, output lengths, compaction and quantization affect wall time. A NO-GO under those thresholds means the planned campaign is not practical with the tested configurations; it is not proof that the platform cannot run useful local LLMs.
