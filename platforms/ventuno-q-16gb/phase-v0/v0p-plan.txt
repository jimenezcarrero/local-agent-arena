1. Question and what is already known (offline, from committed evidence; D140, pi-smoke-audit.txt)
  In V0e A-retry (D139) pi got a tool call in the model's FIRST reply in 6 of 53 sessions (11 %). Failed first replies
  narrate the steps and invent tool results ("The read tool reported an error: missing.txt does not exist") or end
  after a stray "</think>"; no reply holds tool-call markup that the server failed to parse (peg-native parser, the
  GGUF's template opens <think>). 4 sessions were long generations (~5,800 tokens) cut by pi's 600 s timeout. The
  direct streaming tool gates pass (10/10, 3/3).
  Differences from the Jetson, where pi worked with this model (README: arenas 1-2 3/3 at llama.cpp defaults):
  (a) file: pure Q4_0 (required by the NPU) vs the publisher's Q4_K_M; (b) backend: Hexagon NPU vs CUDA;
  (c) sampling: llama.cpp defaults here; the model card's profile (temp 1.0, top_p 0.95, top_k 20, min_p 0,
  presence_penalty 1.5, repeat 1.0) is in suite/sampling-reference.md, and OPERATING.md item 7 says to measure both;
  (d) server flags: here auto slots (4), flash attention and KV type at their defaults; Jetson -np 1, -fa on,
  q4_0 KV, --jinja explicit.
  This plan isolates (a), (b) and (c). (d) is not varied here.

  chat request (exact body) and raw response; pi and the probes are unchanged (pi's provider "bench" is :8080).

4. Readings (declared; diagnostic leads, not conclusions). Each step measures ONE request (pi's first) under that
  step's conditions, 20 stochastic repeats; it does not measure the pi workflow, other requests or interactions
  between the factors. "Differs" = at least 8/20 first-reply tool calls where the comparison has at most 3/20 (or the
  reverse); Fisher exact p is reported with each comparison. Before attributing a difference to quantization or to
  the backend, the steps' /props (effective sampling, chat template) and the GGUF metadata in the server logs are
  compared; a difference there is reported first.
  - D1 near the V0e rate (<= 3/20): the replay reproduces the first-reply problem; otherwise it depends on context the
    single request does not hold (recorded; the comparisons are then read only between steps).
  - D3 >> D1 (same file, CPU better): a lead that the Hexagon backend's numerics matter for this request.
  - D3 ~ D1 low, D4 >> D3: a lead that the pure Q4_0 file matters; it does not show that the NPU cannot serve agents.
  - D2 >> D1: a lead that the card's sampling helps this request on the NPU; it does not show that it fixes pi's
    workflow (D2's own pi smoke rate is the first indication); any configuration change needs its own plan.
  - All low: none of the three effects is shown for this request; it does not exclude them or their interactions.
  The captured requests and replies are kept for offline reading in every case.

5. Policy: HANG or DEVFAULT anywhere (probes included) -> fault recorded first, recovery by probing without a
  restart, a failing post-run library check kept as extra evidence, STOP. A workload that ran (its RESULT line present, rc 0) is a result whatever its rate. Anything else (missing
  evidence, failed health, a replay HTTP error, no request captured, library or file mismatch) -> STOP. Memory: these
  servers are short-lived; the health floor applies as in every run.

6. Budget: expected about 2-3 h: D1 and D2 about 15-25 min each (10 pi sessions of 20-60 s, plus 20 replays); D3
  and D4 about 40-70 min each (CPU: a 1.6K-token prompt at ~24 tok/s plus reasoning at ~5 tok/s per replay). Step
  caps cover the declared worst case (every pi session and replay at its 600 s limit): NPU 19,000 s, CPU 13,000 s;
  together 64,000 s (about 17.8 h), plus probes, pauses and any recovery. A step that reaches its cap is EVIDENCE and
  stops the diagnostic.
